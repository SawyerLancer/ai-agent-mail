# История переписки

Код: `app/thread_context.py` (чистый, без сети и БД), сбор записей —
`handlers._history_for`, сохранение — `poller._remember_thread_data`, экранирование —
`app/promptsafe.py`. Поток черновика — `draft-review-flow`; безопасность —
`email-actions-safety`; что отдаёт MCP — `mail-mcp` («Заголовки цепочки»).

## Как сейчас

### Источники (по приоритету)
1. **Своя база.** `TrackedEmail` этого же ящика (`account`) с непустым `body_text` —
   прошлые входящие; `Draft` со `status="sent"`, `kind="reply"` и непустым `body` —
   «наш ответ», дата — `sent_at` (у старых записей запасной `updated_at`).
   `_collect_history` не грузит весь ящик: SQL-фильтр по ящику, `body_text != ""`,
   дате (не старше max(окно темы, срок хранения)) и совпадению `norm_subject` ИЛИ
   `sender_addr`; затем до `_HISTORY_REF_ROUNDS=3` дозапросов по Message-ID из
   ссылок. Каждый запрос — **новые сначала**, не больше
   `_HISTORY_MAX_CANDIDATES=200`; при достижении лимита — `log.info` (без адресов),
   старые кандидаты отброшены. Ссылки найденного письма расширяют поиск, только
   если оно `same_party` с текущим отправителем — и после первого запроса, и в
   раундах. Цепочка длиннее трёх звеньев через чужих по адресу (коллег) теряет
   самые ранние письма; у частого собеседника за окном больше 200 писем — старые.
   `Draft sent` — только для писем найденной цепочки. Работа с БД — в
   `asyncio.to_thread`.
   `body_text` — исходный текст (с цитатой), до `BODY_STORE_CHARS=3000`;
   заполняется при публикации карточки из того же ответа `get_body`, вместе с
   `in_reply_to` и `references`. Цитата отрезается при чтении (`split_quote`).
2. **Связь в цепочку — `_by_headers`.** Транзитивно: кандидат связан, если его
   Message-ID есть в In-Reply-To/References текущего или уже принятых, или его
   ссылки пересекаются с ними. **Но принимается, только если `same_party`:** тот
   же точный адрес (без регистра), что у текущего отправителя, либо тот же домен
   и домен не из `PUBLIC_DOMAINS` (+ `PUBLIC_DOMAINS_EXTRA` из `.env`) — коллеги из
   одной компании. `HISTORY_SAME_DOMAIN=false` — только точный адрес.
   **Список публичных доменов неполный**: общий домен хостинга или вуза сойдёт
   за «компанию». Для бота нескольких людей рекомендуем `HISTORY_SAME_DOMAIN=false`. Иначе — отсеян (`log.info` без адресов), и цепочка через него не
   продолжается: ссылки отсеянного в поиск не добавляются. Защита от подделанных
   References: бывший участник копии не вытащит нашу переписку с другим
   человеком. Наши `sent`-ответы привязываются только к принятым письмам.
   Две ветки на один корень от разных людей (gmail): в историю идёт корень и
   ветка текущего собеседника, чужая ветка и наш ответ в ней — нет.
3. **Запасная склейка — `_by_subject`**, только если заголовки ничего не дали и
   выполнено **всё**: текущее похоже на ответ (тема `Re:/RE:/Отв:` или есть
   цитата); `norm_subject` (без `Re/Fwd/Fw/Отв/Пересл`, регистра, ё, лишних
   пробелов) не короче 5 символов и не в `STOP_SUBJECTS` («счёт», «вопрос»,
   «документы»…); **точный** адрес собеседника совпадает (домен — нет: на
   gmail/yandex это чужие люди); кандидат не старше
   `HISTORY_SUBJECT_WINDOW_DAYS=60`.
4. **Цитата текущего письма** режется, только если его In-Reply-To — входящее
   письмо из базы. Наши ответы мимо бота (телефон, веб) в базу не попадают —
   цитата закрывает такие дыры.
5. **`split_quote` — сомневаешься, не режь.** Маркеры: шапка «…пишет:/wrote:/
   написал(а):» — только если в той же строке есть дата, время или «@»
   («Вот что бухгалтер пишет:» — не шапка); блок «>» — только 2+ строк «>»,
   идущий до конца письма (внутри — пустые строки, после — до 5 строк подписи).
   Год сам по себе не признак шапки («с 2019 года пишет:»): нужно время, полная
   дата цифрами, день рядом с месяцем (словом, в любом порядке) или «@». Шапка
   Gmail, перенесённая на две строки («On … 2:05 PM John <» / «a@b.com> wrote:»),
   режется по первой строке — если во второй нет даты, а в первой есть;
   «-----Original Message-----»; блок From:/Sent:. Если перед местом разреза нет
   своего текста (ответ снизу под цитатой) — не режем.
6. **«Отправленные» через IMAP — не используем** (см. расхождения).

### Бюджет
`HISTORY_CHARS=6000`, `HISTORY_MAX_MESSAGES=5`. `fit_budget` идёт от новых к
старым: письмо, которое не влезло, обрезается (`…[обрезано]`), если на него
осталось не меньше `MIN_TRUNCATED_CHARS=200`; меньше — выкидывается вместе со
всем, что старше. `max_messages=0` — пусто. В промпт — в хронологическом порядке.

### Промпт
`render` → `<история_переписки>` с пометкой «может быть неполной», внутри
`<письмо_истории направление="от собеседника|наш ответ" дата="…" от="…">`.
Текст — через `escape`, атрибуты — через `attr` (без кавычек и `<>`). Блок идёт
в `draft_reply` перед `<письмо>` и в `revise` (из `Draft.history_text`, без
повторной сборки). В `SYSTEM`: история — данные; не противоречить обещаниям, не
повторять сказанное, при противоречии не решать за человека; история неполная —
не делать выводов «мы не ответили».

### Черновик и превью
`Draft.history_text` (блок как ушёл в промпт), `history_count` — строка
«_Учтено писем переписки: N_» (при 0 — нет). «Заново» собирает историю заново.

### Проверка фактов
`factcheck.classify(body, sources, plain(history_text))`: нет нигде → «⚠️ Модель
добавила»; есть только в истории → «ℹ️ Из прошлой переписки (проверьте, не
изменилось ли)»; есть в текущем письме или текстах пользователя → ничего.
`plain` убирает только наши теги — адреса `<a@b>` в тексте остаются.

### Что не получает историю
`proofread` (вычитка), `summarize`, `style.learn` — там чужие тексты и входящие;
наши прошлые ответы уже учтены при своей отправке. Есть тесты.

### Ошибки
Любая ошибка сбора → `log.warning`, черновик без истории, как раньше.

## Требования и расхождения
- **Старые письма** (до этой версии) без `body_text`, заголовков и ключей склейки —
  в историю не попадут; остаётся цитата текущего письма. Дозаполнения нет:
  без тела оно бесполезно.
- **Цитата из одной строки «>»** в конце письма не режется (правило «2+ строк») —
  останется в тексте; так задумано.
- **Наш Message-ID неизвестен:** `send_email` его не возвращает. Поэтому ответ
  собеседника на НАШ ответ не даёт права резать цитату (In-Reply-To не из базы) —
  возможны дубли истории; безопасно.
- **«Отправленные» через IMAP не читаем:** на Яндексе в 1.6.2 не работают
  `since`/`to_address`, `subject` чувствителен к регистру (`mail-mcp`). Наши
  ответы — только те, что ушли через бота.
- **Маркеры цитат** вживую видели только у Яндекса/корпоративных («…пишет:», `>`);
  Gmail/Outlook — по распространённым форматам, не проверены.
- **Стоимость:** каждая правка через `revise` заново отправляет всю историю. При
  росте числа правок — передавать историю в сжатом виде. Не сделано.
